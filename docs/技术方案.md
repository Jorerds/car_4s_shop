## 2. 系统分层与目录结构

### 2.1 后端分层（Controller → Service → Repository）

```
backend/
├── app/
│   ├── main.py                # 应用入口、中间件、路由注册
│   ├── core/                  # 配置、日志、安全（JWT/密码）、异常处理
│   ├── api/                   # 路由层：仅做参数解析与响应组装
│   │   ├── deps.py            # 依赖注入：DB 会话、当前用户、角色鉴权
│   │   └── v1/                # auth/ models/ appointments/ sales/ admin/ reports/ files
│   ├── schemas/               # Pydantic 请求/响应模型
│   ├── services/              # 业务逻辑：预约状态机、库存扣减、RBAC 数据范围
│   ├── repositories/          # 数据访问：SQLAlchemy 查询封装
│   ├── models/                # ORM 模型
│   ├── integrations/
│   │   └── sms/               # 短信抽象：base.py(接口) / mock.py / aliyun.py / tencent.py
│   ├── tasks/                 # Celery 任务：发送短信、生成导出文件
│   └── utils/                 # 导出、分页、脱敏等纯函数
├── alembic/                   # 数据库迁移
├── tests/                     # pytest：unit/ + api/
└── requirements.txt
```

**分层约束**：路由层不写 SQL、不含业务规则；Service 层不感知 HTTP；Repository 只做数据存取。函数超过 50 行必须拆分。

### 2.2 前端结构

```
frontend/
├── src/
│   ├── api/                   # axios 封装 + 各模块接口定义
│   ├── stores/                # Pinia：用户态、对比栏
│   ├── router/                # 按角色动态注册路由
│   ├── h5/                    # 顾客端页面（TailwindCSS）：首页/列表/详情/对比/预约/我的
│   └── admin/                 # 管理端页面（Element Plus）：车型/时段/预约确认/跟进/报表
└── vite.config.ts             # 多页入口构建
```

## 3. 数据库设计

### 3.1 表清单

| 表                     | 说明                              |
| --------------------- | ------------------------------- |
| `user`                | 用户（顾客/销售/管理员），含角色、手机号或账号、密码哈希   |
| `car_model`           | 车型：名称、品牌、车系、指导价、车身类型、能源类型、状态     |
| `car_model_image`     | 车型图片集：URL、排序、是否主图               |
| `car_model_config`    | 配置参数：车型ID、分组(动力/底盘/…)、参数名、参数值   |
| `test_drive_vehicle`  | 试驾车：车牌号、所属车型、状态                 |
| `test_drive_slot`     | 试驾时段：车型、日期、小时时段、容量、已约数          |
| `appointment`         | 预约：状态机主体，关联车型/时段/销售/试驾车         |
| `test_drive_record`   | 试驾记录：关联预约、评分、反馈文字、实际试驾时间        |
| `customer`            | 客户线索：手机号唯一、姓名、归属销售、状态           |
| `follow_up_record`    | 跟进记录：客户、类型(电话/到店/试驾/成交)、内容、下次跟进时间 |
| `notification`        | 站内消息：接收人(手机号)、内容、已读标记           |
| `audit_log`           | 审计日志：关键操作与导出行为留痕                |
| `model_stat_daily`    | 车型热度日统计：浏览量、对比次数（报表数据源）         |

### 3.2 关键表结构

**`test_drive_slot`（时段库存）**

| 字段            | 类型           | 说明                        |
| ------------- | ------------ | ------------------------- |
| id            | BIGINT PK    |                           |
| model_id      | BIGINT FK    | 车型                        |
| slot_date     | DATE         | 日期                        |
| time_slot     | CHAR(5)      | 时段起点，如 `09:00`（粒度 1 小时）   |
| capacity      | INT          | 可约容量                      |
| booked_count  | INT          | 已占用名额（含待确认）               |

- 唯一约束：`(model_id, slot_date, time_slot)`；
- 查询余量：`capacity - booked_count > 0`。

**`appointment`（预约）**

| 字段            | 类型         | 说明                                            |
| ------------- | ---------- | --------------------------------------------- |
| id            | BIGINT PK  |                                               |
| customer_name | VARCHAR    | 顾客姓名                                          |
| customer_phone| VARCHAR    | 手机号（加密存储）                                     |
| customer_id   | BIGINT FK  | 关联客户线索                                        |
| model_id / slot_id | BIGINT FK | 车型 / 时段                                   |
| status        | ENUM       | 待确认/已确认/已拒绝/已取消/已完成/已爽约                       |
| sales_id      | BIGINT FK  | 处理销售                                          |
| vehicle_id    | BIGINT FK  | 分配的试驾车                                        |
| reject_reason | VARCHAR    | 拒绝原因                                          |
| remark        | VARCHAR    | 顾客备注                                          |

- 部分唯一索引（MySQL 用生成列实现）：`(customer_phone, model_id, slot_date)` 仅对有效状态生效，落实"同号同车型同日仅 1 条有效预约"。

**`car_model_config`（配置参数，键值对）**

| 字段        | 说明                        |
| --------- | ------------------------- |
| model_id  | 车型                        |
| group_name| 分组：动力/底盘/车身/安全/舒适/科技      |
| param_name / param_value | 参数名 / 参数值      |

> 选键值对而非宽表：各车型配置项差异大、需动态增删，宽表无法承载；对比功能按参数名对齐即可。

### 3.3 并发防超约（核心设计）

时段库存扣减必须原子化，采用 **数据库条件更新** 而非"先查后改"：

```sql
UPDATE test_drive_slot SET booked_count = booked_count + 1
WHERE id = :slot_id AND booked_count < capacity;
-- 影响行数为 0 → 库存不足，预约失败
```

- 该 UPDATE 与预约 INSERT 放在**同一事务**中，失败整体回滚；
- 取消/拒绝时在事务内 `booked_count - 1` 释放名额；
- Redis 仅用于"防重复提交"分布式锁（同手机号 + 同车型 + 同日，5 秒 TTL），不作为库存权威来源。

## 4. 接口设计

### 4.1 统一约定

- RESTful 风格，统一前缀 `/api/v1`；
- 统一响应体：`{"code": 200, "message": "成功", "data": ...}`；业务错误码非 200 时 message 给出可读原因；
- 鉴权：`Authorization: Bearer <JWT>`；角色权限由后端依赖注入逐项校验；
- 列表接口统一分页参数：`page` / `page_size`，返回 `total`。

## 5. 关键专项设计

### 5.1 短信服务抽象

```python
class SmsSender(Protocol):
    def send_code(self, phone: str, code: str) -> bool: ...
    def send_notify(self, phone: str, template: str, params: dict) -> bool: ...
```

- `MockSmsSender`：开发/测试默认实现，短信内容写结构化日志，验证码同时写入 Redis 供测试读取；
- `AliyunSmsSender` / `TencentSmsSender`：上线前按选定服务商实现；
- 通过配置项 `SMS_PROVIDER=mock|aliyun|tencent` 在工厂函数中切换，业务代码只依赖 `SmsSender` 接口；
- 发送动作投递 Celery 异步执行，失败自动重试 3 次并告警日志。

### 5.2 认证与 RBAC

- JWT 载荷：`user_id + role`，有效期 12 小时，顾客端滑动续期；
- 依赖注入鉴权：`require_role("sales")`、`require_role("admin")`；
- 数据范围控制：销售查询强制附加 `sales_id = 当前用户` 条件，管理员不加。

### 5.3 短信验证码

- 生成 6 位随机码，存 Redis：`sms:code:{phone}`，TTL 5 分钟，验证后即删；
- 防刷：同号码 60 秒内仅 1 条、单号码单日 ≤ 10 条（Redis 计数器）。

### 5.4 报表与导出

- 报表查询走 MySQL 聚合 SQL；车型热度由浏览/对比事件当日累加写入 `model_stat_daily`；
- 导出为异步任务：POST 提交 → Celery 生成文件存 `/data/exports` → 站内消息附下载链接（24 小时有效）；
- 导出行为写入 `audit_log`（操作人、报表类型、时间）。

### 5.5 日志与追踪

- 结构化 JSON 日志（loguru），每请求生成 `request_id` 贯穿全链路；
- 关键操作（预约提交/确认/分配/导出）记录 INFO 级业务日志，含操作人与实体 ID。

## 7. 部署方案

- `docker-compose.yml` 编排 5 个服务：`nginx`、`backend`、`celery-worker`、`mysql`、`redis`；
- MySQL 数据卷每日 `mysqldump` 定时备份，保留 7 天；`/data/uploads` 图片目录同步备份；
- 环境差异通过 `.env` 注入（数据库连接、Redis、JWT 密钥、短信服务商配置）；
- 上线 checklist：HTTPS 证书、短信服务商切换为真实实现、管理员初始账号、时段计划初始化。

## 8. 一期技术边界（明确不做）

- 微服务拆分、Kubernetes 编排（单店规模，单机 Compose 足够）；
- Elasticsearch（列表筛选用 MySQL 索引即可）；
- WebSocket 实时推送（通知用"站内消息 + 短信"，轮询拉取）；
- 单元测试之外的重型测试基建（性能压测二期按需补充）。
